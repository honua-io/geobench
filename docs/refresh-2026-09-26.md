# September 2026 evidence refresh

This investigation uses a shared WSL development host. Short repeated runs are
diagnostic evidence, not a replacement for the five-run headline campaign on an
idle dedicated machine. Exact images, dataset checksum, resource limits, and
host information are recorded with the runs.

## Invalid historical baseline

The July `v2026.1-rc.0` archive is **invalid performance evidence**. Its baseline
records error rates of 99.563% (attribute filters), 99.656% (bbox), and 99.503%
(concurrent). One raw attribute-filter run contains 862,925 failed HTTP status
checks and only 5,000 successful requests. The previous report displayed request
throughput and latency while leaving per-scenario error cells blank.

The release workflow continued after k6 failures; regression comparison measured
relative performance against an already-invalid baseline. Completeness checks
did not enforce absolute response correctness. A fresh reproduction against
Honua source revision `e062a12f399771d2c020597511705325351a74b7` confirmed HTTP 429
responses with `rate_limit_exceeded`, and server logs reported a 1,000-request
IP limit. This proves the current configuration problem; the historical archive
does not retain status-code logs sufficient to prove every July failure was 429.

The benchmark Compose profile now explicitly sets `RateLimiting__Enabled=false`.
This is an isolated capacity-test setting, not a change to production security
configuration. Exact response caching remains disabled and database admission
and pool limits remain fixed at 6/6/3.

Every run must now have traffic, passing response checks, and zero HTTP/semantic
errors (including warmup) before it can be resumed, reported as performance, or
promoted into a baseline. Failed runs remain diagnostic artifacts. Reports carry
machine-readable validity and failure reasons. The July baseline is retained
with `valid: false`, and its report has been regenerated to exclude failed rows.

## GeoServer packaging

The default standards profile has been updated from 2.28.0 to **3.0.1**, the
stable release listed by the [official download page](https://geoserver.org/download/)
at the time of this refresh. OGC API Features requires `ogcapi-features`.

GeoServices REST needs the **GSR community extension**. Official
[installation instructions](https://docs.geoserver.org/3.0.x/en/user/community/gsr/installing/)
require a matching nightly package. The supplementary `docker-compose.gsr.yml`
profile pairs the 3.0.x image with 3.0.x extension URLs and enables `gsr`.
The inspected 3.0.x image embeds `main` plugin URLs; overriding these prevents
silently mixing the next development branch into the comparison. Stable and
nightly/GSR results must be labelled separately. The adapter verifies the
FeatureServer query endpoint before running native-protocol benchmarks.

Runtime receipts record installed GeoServer JAR hashes because startup-installed
extensions are not covered by the base Docker image digest.

## Honua optimization findings

Actual SQL sampled during the successful capacity run reads `public.bench_points`
directly, rather than the `public.features` copy that the historical adapter
still populates. The source table has the same dataset indexes as GeoServer.
The feature-store expression indexes therefore do not accelerate these OGC
requests. Keep this distinction when interpreting the April comparison.

The source-backed `PostgresStorageMappedFeatureReader` returns WKB geometry and
JSON attributes, deserializes attributes into dictionaries, and constructs
features for another serialization pass. It does not implement the
`IPagedRawGeoJsonFeatureStore` interface that enables the existing OGC raw-JSON
path in the native feature-store reader. This is a concrete optimization
candidate, not a measured implementation win. Any implementation must preserve
row/field authorization, identifiers, CRS transformations, null geometries,
filtering, sorting, and paging, and earn a before/after benchmark on the same
source-backed layer.

Do not increase pool size or enable response caching to obscure this cost.
Database-admission tuning belongs in a named, independently measured profile.
