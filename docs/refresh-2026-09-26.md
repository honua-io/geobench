# September 2026 evidence refresh

This investigation uses a shared WSL development host. Short repeated runs are
diagnostic evidence, not a replacement for the five-run headline campaign on an
idle dedicated machine. Exact images, dataset checksum, resource limits, and
host information are recorded with the runs.

The current work is an **optimization pass**, not a publication campaign. The
local comparison was stopped and the two hosted smoke workflows were cancelled
to focus on Honua. After disabling benchmark-only rate limiting, the three local
core repetitions passed their HTTP and semantic checks, but timings varied
substantially and one concurrency run recorded a negative duration. Those clock
and contention symptoms make the run unsuitable for performance claims. A
dedicated campaign remains separate work.

## Invalid historical baseline

The July `v2026.1-rc.0` archive is **invalid performance evidence**. Its baseline
records error rates of 99.563% (attribute filters), 99.656% (bbox), and 99.503%
(concurrent). One raw attribute-filter run contains 862,925 failed HTTP status
checks and only 5,000 successful requests. The previous report displayed request
throughput and latency while leaving per-scenario error cells blank.

The release workflow continued after k6 failures; regression comparison measured
relative performance against an already-invalid baseline. Completeness checks
did not enforce absolute response correctness. A fresh reproduction against
Honua source revision `e062a12f399771d2c020597511705325351a74b7` confirmed HTTP 429
responses with `rate_limit_exceeded`, and server logs reported a 1,000-request
IP limit. This proves the current configuration problem; the historical archive
does not retain status-code logs sufficient to prove every July failure was 429.

The benchmark Compose profile now explicitly sets `RateLimiting__Enabled=false`.
This is an isolated capacity-test setting, not a change to production security
configuration. Exact response caching remains disabled and database admission
and pool limits remain fixed at 6/6/3.

Every run must now have traffic, passing response checks, and zero HTTP/semantic
errors (including warmup) before it can be resumed, reported as performance, or
promoted into a baseline. Failed runs remain diagnostic artifacts. Reports carry
machine-readable validity and failure reasons. The July baseline is retained
with `valid: false`, and its report has been regenerated to exclude failed rows.

## GeoServer packaging

The default standards profile has been updated from 2.28.0 to **3.0.1**, the
stable release listed by the [official download page](https://geoserver.org/download/)
at the time of this refresh. OGC API Features requires `ogcapi-features`.

GeoServices REST needs the **GSR community extension**. Official
[installation instructions](https://docs.geoserver.org/3.0.x/en/user/community/gsr/installing/)
require a matching nightly package. The supplementary `docker-compose.gsr.yml`
profile pairs the 3.0.x image with 3.0.x extension URLs and enables `gsr`.
The inspected 3.0.x image embeds `main` plugin URLs; overriding these prevents
silently mixing the next development branch into the comparison. Stable and
nightly/GSR results must be labelled separately. The adapter verifies the
FeatureServer query endpoint before running native-protocol benchmarks.

Runtime receipts record installed GeoServer JAR hashes because startup-installed
extensions are not covered by the base Docker image digest.

The release workflow permits custom server/track selections only with
`evidence_only=true`; release archives and baseline checks retain the Honua core
profile and archive only after the regression gate passes. Enabling GSR with no
image override selects `3.0.x` automatically. Pin that profile using
`docker.osgeo.org/geoserver:3.0.x@sha256:<digest>`; stable-image overrides are
rejected before provisioning. Reports use the orchestrator's shared support
matrix to require all configured runs, including wholly missing optional tracks.
An explicit `save_baseline=true` may replace an invalid historical baseline only
after every new run passes validation. Valid old baselines still undergo normal
regression comparison; this opt-in never permits failed new evidence.

## Honua optimization findings

Actual SQL sampled during the successful capacity run reads `public.bench_points`
directly, rather than the `public.features` copy that the historical adapter
still populates. The source table has the same dataset indexes as GeoServer.
The feature-store expression indexes therefore do not accelerate these OGC
requests. Keep this distinction when interpreting the April comparison.

The source-backed `PostgresStorageMappedFeatureReader` returns WKB geometry and
JSON attributes, deserializes attributes into dictionaries, and constructs
features for another serialization pass. It does not implement the
`IPagedRawGeoJsonFeatureStore` interface that enables the existing OGC raw-JSON
path in the native feature-store reader. This is a concrete optimization
candidate, not a measured implementation win. Any implementation must preserve
row/field authorization, identifiers, CRS transformations, null geometries,
filtering, sorting, and paging, and earn a before/after benchmark on the same
source-backed layer.

Do not increase pool size or enable response caching to obscure this cost.
Database-admission tuning belongs in a named, independently measured profile.

Two narrower paths are worth investigating before another load campaign:

- Both the native and source-backed readers deserialize each attribute object
  into a temporary dictionary of JSON values, copy/convert it into a pooled
  dictionary, then create an immutable dictionary. A single document parsed into
  the pooled dictionary can remove the intermediate allocations. Validate CLR
  scalar types, nested JSON lifetimes, dictionary reuse, and allocated bytes per
  row; elapsed time on the shared host is not a reliable acceptance criterion.
- Sampled numeric-filter SQL casts physical numeric columns to text and back to
  numbers (`NULLIF(NULLIF((temperature)::text, ''), '')::double precision`).
  Compare its query plan with a typed-column predicate before changing the
  translator. JSONB-backed fields still need conversion and empty-value handling.

Native source-backed MVT uses `ST_AsMVT` and `ST_AsMVTGeom` in PostGIS directly.
It bypasses the managed attribute reader, so attribute-parser savings must not
be claimed for that tile path. Profile uncached SQL/geometry work separately
from feature-based map rendering and cache hits.

## First allocation optimization

Honua branch `perf/source-backed-attributes` replaces the intermediate attribute
dictionary in both Postgres readers with one scoped `JsonDocument`, cloning
nested values that must outlive that document. The focused Release test run
passed **90 tests**, covering the new reader and the existing source-backed
reader suites (including real PostGIS integration tests).

The retained allocation regression test compares the previous implementation
with the new reader, warms both paths, and measures thread-local managed bytes
for 1,000 iterations of an 11-field scalar row. Both paths include the final
immutable dictionary copy. On .NET 10.0.11 it measured **4,552 → 1,744 bytes per
row**, a **61.7% reduction for this materialization step**. This is neither an
end-to-end allocation measurement nor a latency/throughput or Native AOT result.

Reproduce from that Honua branch (use the shared build-lock wrapper on a shared
development host):

```bash
dotnet test tests/dotnet/Honua.Db.Postgres.Tests/Honua.Postgres.Tests.csproj \
  --configuration Release \
  --filter FullyQualifiedName~FeatureAttributeJsonReaderTests \
  --logger 'console;verbosity=detailed'
```

Correctness coverage includes CLR numeric types, nulls, nested JSON after
document disposal, escaped names, Unicode, and pooled-dictionary reuse. The
test has a relative allocation budget to detect a return of the intermediate
dictionary/per-scalar documents without depending on wall-clock timing.

## Controlled optimization pass, September 27 Hawaii / September 28 UTC

With the host available for testing, a new native AOT run isolated a PostGIS
parallel-plan bottleneck. This supersedes the earlier noisy timing observations
for this specific workload; it remains a short optimization experiment, not a
release baseline or cross-product comparison.

Image: `ghcr.io/honua-io/honua-server@sha256:a276c0a40d30536b1c8cb4567397fa6160aa057f44cc7eb8c65c874a8a830d57`,
OCI revision `bbd48b43bbf38b70d7e114286f829c2cab156cec` (includes the numeric-filter
and single-feature lookup fixes). Both arms used GeoBench `459f99f`, identical
100k-point data and images verified by runtime receipts, 4 CPU / 4 GiB per
container, 10 VUs, 100-feature pages, exact response caching off, and adaptive
admission off. Three consecutive runs per arm used 30-second warmup and
30-second measured scenarios. The default arm ran first; order was not randomized.
An unrelated local stack remained up with light background activity; heavy work
was excluded with the shared build locks.

Only the PostgreSQL setting `max_parallel_workers_per_gather` changed, from 2 to
0. Each arm used a freshly provisioned isolated stack. All six runs passed HTTP
and semantic checks with zero errors (126,483 requests including warmup).

| Scenario | Default req/s | Serial req/s | Default p95 ms | Serial p95 ms |
| --- | ---: | ---: | ---: | ---: |
| Medium bbox | 143.2 | 360.8 | 106.96 | 50.40 |
| Large bbox | 153.3 | 356.13 | 102.35 | 49.64 |

Medians across three runs: **2.3–2.5x throughput and 51–53% lower p95**.
Throughput is scenario request count / its measured window, excluding warmup.
Sampled median CPU changed from PostGIS ~403% / Honua ~158% to PostGIS ~278% /
Honua ~397% (includes warmup and gaps), moving the bottleneck into the application.

Alternating isolated SQL replays of three observed bbox queries retained
identical returned-row hashes. Five measured samples per setting after warmup
had median execution times of 13.006 → 1.198 ms, 12.046 → 1.577 ms, and
16.548 → 13.139 ms. Default plans used Gather Merge, including parallel
primary-key scans for the first two probes. Queries retained spatial predicates,
stable ordering, and `LIMIT 101`.

Do not turn this into a global production default without coverage for other
selectivities, counts, aggregates, larger pages, and analytical work. Follow-up:
[honua-server #5275](https://github.com/honua-io/honua-server/issues/5275).
Configured pool/admission limits of 6/6/3 still do not govern the source-bound
feature-read path; [#5264](https://github.com/honua-io/honua-server/issues/5264)
tracks enforcement. Policy queries do use the managed gate, so its activity
cannot be generalized to all source-bound database traffic.

Raw receipts, SQL plans, logs, six run JSON files, comparison script, and exact
Compose override are retained locally in `results/20260927-parallel-default`,
`results/20260927-parallel-disabled`, `results/20260927-controlled-screen`, and
`results/20260927-optimization`. Reports were regenerated with the runtime-receipt
classification fix; raw k6 JSON was unchanged. The initial screen's GeoServices
diagnostic is invalid because geometry + ID requests used `objectid` instead of
the published `id`. It is retained for audit and excluded from these results.

Reproduce with the pinned image and `SERVERS=honua TESTS=spatial-bbox RUNS=3
SPATIAL_BBOX_WARMUP=30s SPATIAL_BBOX_DURATION=30s
SPATIAL_BBOX_SCENARIOS=medium,large DIAGNOSTICS=1
POSTGIS_LOG_MIN_DURATION_STATEMENT=100 DIAGNOSTICS_INTERVAL_SECONDS=3`.
Use a separate timestamp for each arm. The serial Compose override preserves
`max_connections=200` and `log_min_duration_statement=100`, adding only
`max_parallel_workers_per_gather=0` to the PostGIS command.

Memory sampling during the initial successful core screen showed managed-memory
reclamation around natural Gen2 collections. Container memory ranged
212.9–347 MiB; sampled managed estimates ranged 72.7–185.1 MiB. This is neither a
retained-heap measurement nor a leak-free verdict; the known pool-rotation
ownership issue remains [#5265](https://github.com/honua-io/honua-server/issues/5265).

The corrected GeoServices diagnostic subsequently passed all eight variants:
39,869 requests including warmup, 119,607 successful checks, zero errors. Its
receipt records `id` as the projected ID field. This single run validates the
benchmark fix and supplies screening data, not a repeated tuning comparison.
